# Reflex test guide

The Reflex test suite validates MCP behavior against a real Windows environment. It is intentionally split between ordinary regression coverage and tests that can change, inspect, or visibly affect the host machine.

## Run the suites

```powershell
npm run check              # syntax check for mcp-server.js
npm test                   # standard regression suite
npm run test:dangerous     # includes explicitly opted-in live-machine tests
npm run ux:smoke           # controlled UX runner scenario
npm run ux:visible         # visible mouse/window demonstration
npm run ux:agent-mode      # visible agent-mode parity scenario
```

Run the ordinary suite first. The dangerous and visible commands are opt-in because they can execute commands, interact with processes/windows, change the clipboard, or move the cursor. Close unrelated applications and do not use them during an unsupervised desktop session.

## Layout

Each focused regression test lives in its own directory and contains:

- `TEST_SPEC.md` — tool name, risk category, goal, expected response fields, and named cases
- `test.js` — executable test logic
- `last_result.json` — newest result artifact for that test, generated by the runner

Run-level output is written to:

- `logs/latest_ai.json` — machine-readable aggregate result for automation and diffs
- `logs/latest_human.md` — concise review-oriented summary
- `logs/runs/<timestamp>/` — immutable per-run evidence

Generated result files describe the machine and moment that produced them. They are evidence, not documentation: do not edit them manually to hide a failure.

## Safety behavior in tests

The runner normalizes control state around tests where appropriate using `reset_emergency_stop` and `resume_control`. That setup does not make a test harmless. A test that requests visible control, touches the clipboard, launches/focuses an application, runs a command, or inspects live processes can still affect the active Windows session.

`REFLEX_DISABLE_OVERLAY=1` is permitted only for non-interactive automation of control-lease behavior. It disables the user-visible overlay while retaining server-side control state; it must not be treated as a normal end-user mode.

## Reading results

A result is useful only when it records all three of these facts:

1. The intended tool contract was exercised.
2. The expected behavior or failure mode occurred.
3. Any host-dependent limitation is reported clearly.

For example, window-focus tests can fail when Windows prevents the test process from taking foreground focus. That should be reported as an environmental failure with the observed error, not silently converted into a passing assertion.

## Adding a test

1. Put the test under the family that matches its capability and risk.
2. Add `TEST_SPEC.md` with a concise, reviewable contract.
3. Exercise success, invalid input, and a realistic failure or boundary path.
4. Mark tests that can affect the host as dangerous and keep them out of the standard suite unless they can be safely isolated.
5. Run the applicable suite and inspect both the AI JSON and human summary.
